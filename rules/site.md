# Documentation site

How docstrings become a published site via Documenter.jl and
`CTBase.automatic_reference_documentation()`. Generic examples. Complements
[`docstrings.md`](docstrings.md) (what to write *inside* docstrings). For *building*
the docs (draft-first workflow, local preview), see [`method.md`](../method.md).

Identifiers: `SITE1`–`SITE17` (see [`README.md`](../README.md#rule-identifiers)).

## Backend

Two backends are used in the ecosystem; DocumenterVitepress is the current standard.

| Backend | Format | Node.js |
| --- | --- | --- |
| `Documenter.jl` | classic HTML | not required |
| `DocumenterVitepress` | VitePress site | required |

Selected via the `format` keyword in `makedocs`:

```julia
# Documenter.jl (classic)
format = Documenter.HTML(...)

# DocumenterVitepress
format = DocumenterVitepress.MarkdownVitepress(; repo=..., devbranch=..., devurl=...)
```

Both backends use the same Julia API (`makedocs`, `with_api_reference`, `InterLinks`,
`draft`). DocumenterVitepress adds a `docs/src/.vitepress/` directory for the VitePress
site configuration and requires `node_modules/` in `docs/` (gitignored; install once
with `npm install` from `docs/`).

## Layout

```text
docs/
├── make.jl              # entry point; uses with_api_reference()
├── api_reference.jl     # generate_api_reference() + with_api_reference() + cleanup
├── inventories/         # InterLinks fallback inventories (one per dependency)
└── src/
    ├── .vitepress/      # VitePress config (DocumenterVitepress only)
    ├── index.md         # landing page
    ├── <topic>/         # hand-written guides
    └── api/             # auto-generated (removed after build)
```

## SITE1 — The API reference is generated, never hand-written

**Rule.** API pages are generated by `CTBase.automatic_reference_documentation`, through
`with_api_reference()` in `make.jl`; `api_reference.jl` provides
`generate_api_reference` / `with_api_reference` / cleanup
([`SITE10`](#site10--with_api_reference-takes-both-directories-and-always-cleans-up)).
No API page is written by hand.

**Why.** A generated reference cannot drift from the docstrings, and covers every
symbol.

**Check.** `exact` (to be tooled): `docs/make.jl` calls `with_api_reference`, and no
page under `docs/src/` contains a hand-written `@docs` block for package symbols.

## SITE2 — One public page per submodule, one unified Internals page

**Rule.** Public and private symbols are both documented, separately: one flat page per
submodule for exported symbols (`public=true, private=false`); one unified "Internals"
page for all private symbols across all submodules and extensions
(`public=false, private=true`). The standard pattern uses a shared `modules_config` list
to avoid repeating file lists, then generates public pages in a loop and one unified
Internals page.

```julia
# ── Shared config: one entry per submodule ────────────────────────────────────
modules_config = [
    (mod=MyPackage.SubA, title="SubA", filename="suba", files=src(
        "SubA/SubA.jl", "SubA/types.jl", "SubA/helpers.jl",
    )),
    (mod=MyPackage.SubB, title="SubB", filename="subb", files=src(
        "SubB/SubB.jl", "SubB/core.jl",
    )),
]

EXCLUDE = Symbol[:include, :eval]

# ── Public pages: one flat page per submodule ─────────────────────────────────
pages = [
    CTBase.automatic_reference_documentation(;
        subdirectory = "api",
        primary_modules = [cfg.mod => cfg.files],
        exclude  = EXCLUDE,
        public   = true,
        private  = false,
        title    = cfg.title,
        filename = cfg.filename,
    )
    for cfg in modules_config
]

# ── Internals: all private symbols in one page, sections by module ────────────
internals_modules = Any[cfg.mod => cfg.files for cfg in modules_config]

# Extensions are detected and added conditionally (SITE3)
for (sym, files) in [
    (:MyExt, ext("MyExt/MyExt.jl", "MyExt/helpers.jl")),
]
    extmod = Base.get_extension(MyPackage, sym)
    isnothing(extmod) || push!(internals_modules, extmod => files)
end

push!(pages, CTBase.automatic_reference_documentation(;
    subdirectory                 = "api",
    primary_modules              = internals_modules,
    external_modules_to_document = [MyPackage],
    exclude                      = EXCLUDE,
    public                       = false,
    private                      = true,
    title                        = "Internals",
    filename                     = "internals",
))
```

The resulting navigation is:

```text
API Reference
    SubA        ← exported symbols only
    SubB        ← exported symbols only
    Internals   ← all private symbols, sections by module (including extensions)
```

Keep the per-submodule file lists in sync with `src/` — a missing file silently drops
docstrings and breaks `@ref` links.

**Why.** Users reach internals via qualified paths ([`MOD8`](modules.md#mod8--two-level-exports)),
so internals are part of the documented surface — but kept out of the main navigation.

**Check.** `exact` (to be tooled): every file under `src/<Sub>/` appears in the file
list of its submodule.

## SITE3 — Extensions documented when present

**Rule.** Extensions are detected with `Base.get_extension` and added to the reference
when loaded (see the loop in [`SITE2`](#site2--one-public-page-per-submodule-one-unified-internals-page)).
An extension tightly coupled to a module (e.g. a Plots extension for a Display module)
may instead be listed as an additional entry in `primary_modules` of the parent page:

```julia
CTBase.automatic_reference_documentation(;
    subdirectory="api",
    primary_modules=[
        MyPackage.Display => src(joinpath("Display", "Display.jl"), ...),
        MyPackagePlots    => ext("CTMyPackagePlots.jl", ...),    # ← grouped here
    ],
    external_modules_to_document=[Plots],
    exclude=EXCLUDE_BASE,
    public=true, private=true,
    title="Display & Plots",
    title_in_menu="Display & Plots",
    filename="api_display",
),
```

**Why.** An extension's methods are part of the API whenever its weak dependency is
loaded; a missing page hides them.

**Check.** `exact` (to be tooled): every module under `ext/` is listed in
`api_reference.jl`.

## SITE4 — Every `@extref` is backed by `InterLinks`

**Rule.** If `@extref` is used, `InterLinks` is set up and passed via `plugins=[links]`,
with one entry per referenced package:

```julia
using DocumenterInterLinks
links = InterLinks(
    "OtherPkg" => ("https://.../OtherPkg.jl/stable/",
                   "https://.../OtherPkg.jl/stable/objects.inv",
                   joinpath(@__DIR__, "inventories", "OtherPkg.toml")),
)
makedocs(; plugins=[links], ...)   # makes [`OtherPkg.Sub.Sym`](@extref) resolve
```

The third element is a fallback inventory *location* — `InterLinks` tries each entry in
order and uses the first reachable one. It can be a URL or a local file path.

### Local fallback for sibling packages (cross-repo development)

While developing across sibling repos — e.g. `Pkg.develop`-ing a sibling package to
verify an in-progress change before it is released — point that package's `InterLinks`
entry at the sibling's own local build output instead of only its published URL, so
cross-package `@extref`s are verifiable without a release:

```julia
"OtherPkg" => (
    "https://.../OtherPkg.jl/stable/",
    joinpath(@__DIR__, "..", "..", "OtherPkg.jl", "docs", "build", "1", "objects.inv"),
    "https://.../OtherPkg.jl/stable/objects.inv",
),
```

Same "first reachable wins" mechanism — falls back to the published inventory once the
sibling's local build doesn't exist (e.g. in CI, where sibling repos aren't checked out
side by side).

**Why.** Cross-references resolve at build time; an `@extref` without an inventory is a
broken link.

**Check.** `exact` (to be tooled): every package named in an `@extref` target has an
`InterLinks` entry.

## SITE5 — Self-reference for extensible generics

**Rule.** A package whose shared generics get extended by downstream packages (see
[`DOC5`](docstrings.md#doc5--self-reference-for-extensible-generics)) registers
**itself** as an `InterLinks` target, local build path checked before the published
URL:

```julia
links = InterLinks(
    "MyPackage" => (
        "https://.../MyPackage.jl/stable/",
        joinpath(@__DIR__, "build", "1", "objects.inv"),  # this repo's own last build
        "https://.../MyPackage.jl/stable/objects.inv",
    ),
    ...
)
```

**Why.** Its own `@extref` cross-submodule references must resolve both in its own
build and when transcluded into a downstream package's docs. The local path is checked
first, so the self-references are verifiable from a plain local build — no publish
required. It only fails to resolve on the very first build of a fresh docs setup (no
local inventory exists yet); every build after that resolves against the
freshly-produced one. On that first build, expect `DocumenterInterLinks` to log a
`cannot resolve external link` `@error` for every self-referenced symbol — this is
non-fatal (`makedocs` still completes) and is not a sign the setup is broken; just run
`make.jl` a second time.

**Check.** `exact` (to be tooled): a package using `@extref` on its own name has a
self-entry whose local path comes before the published one.

## SITE6 — Guides are hand-written and separate from the API

**Rule.** Narrative guides are hand-written under `docs/src/<topic>/`; the API reference
is generated and cleaned up after the build.

**Why.** Guides explain; the reference lists. Mixing them makes both harder to
maintain.

**Check.** `judgment`.

## SITE7 — Submodule imports in guides

**Rule.** `@setup`/`@example` cells that call one submodule repeatedly bring in the
**submodule name only** — `using Pkg: Sub`, never `using Pkg.Sub`. As everywhere else,
`import` is not an option ([`MOD3`](modules.md#mod3--no-import)).

```julia
# ✅ short, qualified, no export leakage
using CTBase: Data, Traits

Data.VectorField(x -> -x)
Traits.time_dependence(vf)
```

```julia
# ❌ the dotted form leaks Data's exports — bare `VectorField(...)` silently also works
using CTBase.Data
```

For a guide that touches a submodule only once or twice, skip that line and fully
qualify instead: `using CTBase` then `CTBase.Sub.symbol(...)` — the package top level
exports nothing, so this brings no symbols into scope.

**Why.** The dotted form also pulls `Sub`'s `export`s into scope unqualified, silently
allowing calls the guide never writes (e.g. bare `VectorField(...)` instead of
`Data.VectorField(...)`); the `: Sub` form binds just the name, so every call still
needs the qualified path.

**Check.** `exact` (to be tooled, syntactic) for `using Pkg.Sub` in a code cell.

## SITE8 — The index page is the entry point

**Rule.** `docs/src/index.md` has: a `@meta CurrentModule` block, a one-paragraph scope
statement, info/note/warning admonitions (notably the qualified-access policy), a module
table, guide links via `[@ref]`, and a short Quick Start with qualified calls.

**Why.** A reader landing on the site learns in one page what the package does, how to
call it, and where to go next.

**Check.** `heuristic` (to be tooled): presence of each piece.

## SITE9 — Code cell line width

**Rule.** Lines inside `@example`, `@repl`, `@setup`, and plain ```` ```julia ```` code
blocks stay within **~75 characters**. Long calls are wrapped with each argument on its
own line and a trailing comma:

```julia
# Good — wrapped, each argument on its own line
Strategies.build_strategy(
    :collocation,
    AbstractFakeDiscretizer, registry;
    grid_size = 300,
)

# Bad — single line exceeds 75 chars
Strategies.build_strategy(:collocation, AbstractFakeDiscretizer, registry; grid_size = 300)
```

**Why.** This keeps rendered code readable on narrow screens and avoids horizontal
scrolling in the documentation site.

**Check.** `exact` (to be tooled): line length inside code blocks of `docs/src/`.

## SITE10 — `with_api_reference` takes both directories and always cleans up

**Rule.** `with_api_reference(f, src_dir, ext_dir)` receives the source **and** extension
directories explicitly from `make.jl`, and removes the generated pages in a `finally`
block, whatever the build outcome:

```julia
function with_api_reference(f::Function, src_dir::String, ext_dir::String)
    pages = generate_api_reference(src_dir, ext_dir)
    try
        f(pages)
    finally
        docs_src = abspath(joinpath(@__DIR__, "src"))
        function cleanup(pages)
            for p in pages
                content = last(p)
                if content isa AbstractString
                    fname = endswith(content, ".md") ? content : content * ".md"
                    full_path = joinpath(docs_src, fname)
                    isfile(full_path) && rm(full_path)
                elseif content isa Vector
                    cleanup(content)
                end
            end
        end
        cleanup(pages)
    end
end
```

```julia
# docs/make.jl
src_dir = abspath(joinpath(@__DIR__, "..", "src"))
ext_dir = abspath(joinpath(@__DIR__, "..", "ext"))

include("api_reference.jl")

with_api_reference(src_dir, ext_dir) do api_pages
    makedocs(; ..., pages=["API Reference" => api_pages])
end
```

**Why.** Deriving `ext_dir` from `src_dir` inside the function is fragile if the layout
changes; a failed build must not leave generated pages behind in `docs/src/`.

**Check.** `exact` (to be tooled): signature of `with_api_reference` and the `finally`
block.

## SITE11 — Code annotations only in static fences; pairs stay visible

**Rule.** VitePress fence annotations are used only in non-executed fences, a
before/after is one annotated block, and a correspondence pair is never put in a code
group.

| Feature | Syntax (trailing comment on the line, or on the fence) | Renders |
| --- | --- | --- |
| diff add / remove | `# [!code ++]` / `# [!code --]` | green / red gutter with `+` / `-` |
| error line | `# [!code error]` | red-tinted line |
| warning line | `# [!code warning]` | amber-tinted line |
| highlight | `# [!code highlight]`, or `` ```julia {2,5-7} `` on the fence | tinted background |
| focus | `# [!code focus]` | dims the rest, reveals on hover |
| line numbers | `` ```julia:line-numbers `` | gutter numbering |
| code group | `::: code-group` … `:::` around several fences | tabbed switcher |

The `[!code …]` token is stripped from the rendered comment, so it can sit after real
text: `# paired keywords  [!code ++]` renders as `# paired keywords` on a line marked
added.

**Static fences only.** These annotations are reliable only in non-executed
```` ```julia ```` / ```` ```julia-repl ```` / ```` ```text ```` fences. There is no
support for them inside executed `@example` / `@repl` / `@setup` blocks (the CSP +
transform path drops them). Never annotate a build-verified example. They do work
inside `!!! note` / `!!! warning` admonitions (verified: OptimalControl.jl
`migration.md`).

**Before/after — collapse the pair.** A "write this instead of that" shown as two blocks
becomes one:

````markdown
```julia
f(t0, x0, tf, λ)                    # [!code --]
f(t0, x0, tf; variable=λ)           # [!code ++]
```
````

**No code group for a correspondence pair.** A `::: code-group` is a tabbed switcher —
the reader sees one block at a time. That fits genuine *either/or* alternatives
(`using Plots` vs `using CairoMakie`), never a pair whose point is the line-to-line
mapping (a DSL macro shown next to the function calls it expands to, a before/after).
Keep those stacked and both visible, with the prose that ties them together.

**Why.** An annotation in an executed block is silently dropped; a correspondence
hidden behind tabs loses its point.

**Check.** `exact` (to be tooled) for `[!code …]` inside an executed block; the use of
code groups is a `judgment`.

## SITE12 — Plots are rendered as SVG

**Rule.** With DocumenterVitepress, PNG capture is disabled once, globally, in
`make.jl` — before any `@example` block runs — so every figure is saved as SVG:

```julia
using Plots
using CairoMakie: CairoMakie   # binds the name only: Makie's `plot` / `plot!` stay
                               # out of Main and cannot collide with Plots'
Base.showable(::MIME"image/png", ::Plots.Plot) = false
CairoMakie.activate!(; type = "svg")
Base.showable(::MIME"image/png", ::CairoMakie.Makie.Figure) = false
```

**Why.** DocumenterVitepress selects the output format for `@example` block plots by
picking the MIME type with the **highest priority** among those the plotting library
supports:

| MIME type | Priority |
| --- | --- |
| `image/svg+xml` | 3.0 |
| `image/png` | 4.0 |

PNG wins by default. This is the **opposite** of `Documenter.HTML`, which prefers SVG.
**Both `Plots.jl` and `CairoMakie` respond to `image/png`**, so PNG wins for every figure
unless PNG capture is disabled. DocumenterVitepress then falls back to `image/svg+xml`
and saves each figure as a separate `.svg` file (referenced via `![](filename.svg)`).
Plots' GR backend and CairoMakie both emit standalone SVG with the `xmlns` attribute,
which is what DocumenterVitepress needs.

If you only plot on a few pages, the `Base.showable` line can instead go in a per-page
`@setup` block — but the global form is simpler and does not have to be repeated.

Older guidance said CairoMakie "produces SVG automatically, no action needed" — that is
**not true** with current CairoMakie (0.15): it responds to `image/png` like Plots does.
`Plots.default(fmt=:svg)` has **no effect** on MIME type selection — it only controls
the format used when Plots saves to a file path, not how Documenter captures the result.

**Check.** `exact` (to be tooled): `docs/make.jl` of a package that plots disables
`image/png` for each plotting library it loads.

## SITE13 — Deploy on stable tags only, guard `deploydocs`, previews on request

**Rule.** The documentation workflow triggers on stable tags only, `make.jl` calls
`deploydocs` only when bases were built, and a pull request deploys its preview only when
it carries the `documentation push preview` label.

```yaml
# .github/workflows/Documentation.yml
on:
  push:
    branches:
      - main          # deploys to the `dev/` subfolder
    tags:
      - 'v[0-9]+\.[0-9]+\.[0-9]+'   # v0.26.0 yes, v0.26.0-beta no
  pull_request:
    types: [labeled, synchronize, reopened]

jobs:
  call:
    if: >
      github.event_name != 'pull_request' ||
      (contains(github.event.pull_request.labels.*.name, 'run documentation') &&
        (github.event.action != 'labeled' ||
         github.event.label.name == 'run documentation' ||
         github.event.label.name == 'documentation push preview'))
    uses: control-toolbox/CTActions/.github/workflows/documentation.yml@main
```

```julia
# docs/make.jl
bases_file = joinpath(@__DIR__, "build", "bases.txt")
if isfile(bases_file)
    DocumenterVitepress.deploydocs(;
        repo=repo_url * ".git",
        devbranch="main",
        push_preview=get(ENV, "DOCUMENTER_PUSH_PREVIEW", "false") == "true",
    )
else
    @info "Skipping deployment: no bases were built (prerelease with existing higher stable release)."
end
```

Push to `main` still deploys the `dev` version of the docs. Only pushes of stable tags
trigger the versioned deployment. On a pull request, `run documentation` is the only
trigger; `documentation push preview` is a modifier that also deploys the build to
`previews/PR<n>`, and does nothing on its own. The reusable workflow of CTActions sets
`DOCUMENTER_PUSH_PREVIEW` from that label, and a `DocPreviewCleanup.yml` caller removes the
preview when the PR is closed. The labels, the `if:` guard and the cleanup caller are
described in
[CTActions `docs/WORKFLOWS.md`](https://github.com/control-toolbox/CTActions/blob/main/docs/WORKFLOWS.md).

**Why.** By default a documentation workflow triggers on `tags: '*'`, which includes
prerelease tags such as `v0.26.0-beta`. DocumenterVitepress does **not** deploy
prereleases when a higher stable version with the same major.minor already exists (e.g.
`v0.26.0` already in the registry → `v0.26.0-beta` produces 0 VitePress bases). This
causes `deploydocs` to crash because it expects a `bases.txt` file that was never
written. The guard is a belt-and-suspenders safeguard: if `makedocs` built 0 bases (any
reason), the CI job completes cleanly instead of crashing at `deploydocs`.

A hardcoded `push_preview=true` deploys every PR build, which fills `gh-pages` with
`previews/PR<n>` directories nobody looks at. `opened` is left out of the PR `types`: a
PR created with its labels emits both `opened` and `labeled`, which would build twice.

**Check.** `exact` (to be tooled): tag filter, PR `types` and `if:` guard in
`Documentation.yml`; `bases.txt` guard and `DOCUMENTER_PUSH_PREVIEW` in `make.jl`;
`DocPreviewCleanup.yml` present.

## SITE14 — Pin the npm dependencies of `docs/package.json`

**Rule.** Every dependency in `docs/package.json` is pinned to an exact version: no `^`,
no `~`, no range. This applies to `vitepress` and to every plugin that declares a peer
dependency on it (`@nolebase/*`, `vitepress-plugin-*`), and by default to everything
else. Bump versions deliberately, in a dedicated commit.

```json
{
  "dependencies": {
    "@nolebase/vitepress-plugin-enhanced-readabilities": "2.18.2",
    "vitepress": "1.6.4"
  }
}
```

**Why.** The repository has no lockfile, and DocumenterVitepress runs a plain
`npm install` at build time. A caret range therefore resolves to the latest release on
every build, so one upstream release can break the documentation of every package at the
same time. This happened with `@nolebase/vitepress-plugin-enhanced-readabilities@2.21.x`,
which requires `vitepress@^2.0.0-alpha` while the packages use `vitepress@^1.6.4`:
`npm install` failed with `ERESOLVE` and the build of a release tag failed.

**Check.** `exact` (to be tooled): no version string in `docs/package.json` starts with
`^`, `~`, `>`, `<` or `*`.

## SITE15 — Errors of a missing extension come from a fresh process

**Rule.** An error raised because a weak dependency is not loaded (an `ExtensionError`,
or any error that only exists without the extension) is shown from a **fresh Julia
process** in which only the package is loaded, never from an `@repl` block and never as
hand-written output. The build fails if the example no longer throws.

````markdown
```@eval
Main.CTBase.DevTools.repl_without_extensions(:CTSolvers, "CTSolvers.Solvers.Ipopt()")
```
````

`CTBase.DevTools.repl_without_extensions(package, codes...)` (CTBase ≥ 0.30.10,
`DocumenterReference` extension, loaded by every `make.jl`) runs the snippets in a fresh
process on the docs environment with the docs `LOAD_PATH`, where only `package` is loaded.
It evaluates all but the last, and returns the error of the last one as a
`julia-repl-runs` ANSI block, rendered like an `@repl` block. It throws when the last
snippet succeeds. `make.jl` has `using CTBase`, hence `Main.CTBase` in the page.

**Why.** `make.jl` loads every weak dependency so that the API reference can document
the extensions (`SITE3`), and extension methods are global to the process: no module or
`@setup` scope can hide them. In the build, the constructor that should fail succeeds,
so `@repl` shows a working instance. Hand-written output avoids that but goes stale
silently; the fresh process keeps the example executed and checked.

**Check.** `judgment`: the page shows an error that depends on a missing extension.

## SITE16 — Log records in examples carry no build-machine path

**Rule.** An `@example` block that is meant to show a warning captures its log records
and prints them without the source location, through hidden lines:

````markdown
```@example page
Main.CTBase.DevTools.warnings_without_paths(; show = true) do # hide
CTSolvers.Solvers.Ipopt(bound_relax_factor = 1e-10; mode = :permissive)
end # hide
```
````

`CTBase.DevTools.warnings_without_paths(f; show=false)` (CTBase ≥ 0.30.10) evaluates
`f()` with its log records captured, prints each warning or error as `┌ Warning: …` /
`│ …` / `└ @ Module`, and returns the value of `f()`. With `show = true` it prints the value after the warnings and
returns `nothing` (see the note on printed output below). Variables assigned inside the
block are declared `global` on a hidden line.

**Why.** Documenter prints a log record with its source location,
`└ @ Module /path/on/the/build/machine/file.jl:line`, which publishes local or CI paths
and changes with every machine that builds the page.

**Check.** `exact` (to be tooled): no absolute path in the built pages under
`docs/build/`.

## SITE17 — Device pages run on every build

**Rule.** A page about GPU execution is executed on every build, CPU or GPU. Every block
that needs a device is guarded by `CUDA.functional()` or wrapped in `try/catch`, the
page opens with a note that its output depends on the machine that built it, and its
first block prints which case it is. The workflow passes a GPU runner to CTActions
(`gpu_runner`) so that the published page is rebuilt on a device after the CPU build.

```julia
if CUDA.functional()
    # ... the device code ...
else
    println("No functional GPU on the machine that built this page: ",
            "no device integration.")
end
```

```markdown
!!! note "What you are reading depends on the machine that built this page"
    Every block below is executed when the documentation is built. With a functional
    CUDA device you are reading real GPU output; without one, you are reading what this
    exact code really produces on a machine without a GPU.
```

A package whose documentation has no device page sets no `gpu_runner` and builds on CPU
only.

**Why.** A static GPU page goes stale without anyone noticing, and a page that runs only
on a device cannot be built by a PR or on a GitHub-hosted runner. Guarded blocks keep one
source for both: the CPU build always publishes, the GPU pass (push to `main` and tags,
never failing the workflow) upgrades it with real device output.

**Check.** `judgment`: device code in a docs page is guarded, and the note is present.

## Notes on the VitePress backend (no identifier)

Know-how about the tool rather than conventions of the ecosystem. Migrating a package
from Documenter to DocumenterVitepress is a separate recipe, in
[`ct-agents`](https://github.com/control-toolbox/ct-agents).

- **`@repl` vs `@example` — ANSI colors.** Before `DocumenterVitepress` **v0.3.5**,
  ANSI-colored output from `@repl` was emitted as a ` ```julia ` fence and rendered as
  raw escape sequences. This was fixed in v0.3.5
  ([#373](https://github.com/LuxDL/DocumenterVitepress.jl/pull/373)): colored `@repl`
  output is now rendered as ANSI while the input remains Julia syntax-highlighted.

  | Block type | Behaviour in `DocumenterVitepress` v0.3.5+ | Recommended use |
  | --- | --- | --- |
  | `@example` | ANSI output is rendered correctly | Evaluated examples without REPL formatting |
  | `@repl` | Colored output is rendered correctly; input remains REPL-highlighted | Interactive examples, including colored `show` output |
  | `@ansi` | Intended for examples whose terminal ANSI output is the focus | Explicit ANSI / terminal-output demonstrations |

  For exceptions, `@repl` + `try/catch # hide` +
  `showerror(IOContext(stdout, :color => false), e) # hide` gives a stable, colorless
  error message — a presentation choice, not a workaround required by v0.3.5+:

  ```julia
  try
      # ... your code that may throw ...
  catch e
      showerror(IOContext(stdout, :color => false), e) # hide
  end # hide
  ```

  For versions before v0.3.5, use `@example` or `@ansi` for colored output, or disable
  colors explicitly as above
  ([LuxDL/DocumenterVitepress.jl#321](https://github.com/LuxDL/DocumenterVitepress.jl/issues/321)).

- **Color-aware display functions.** Custom display functions that emit ANSI escape
  codes check `get(io, :color, false)` before applying escape sequences, and propagate
  the `io` argument through all display helpers — colors on in the REPL and GitHub
  Actions, plain text under `IOContext(stdout, :color => false)`:

  ```julia
  _apply_ansi(s, code, io::IO) = get(io, :color, false) ? "\033[$(code)m$(s)\033[0m" : s
  ```

- **Downloadable non-image assets (`Manifest.toml`, data files, archives).** VitePress
  only emits assets it recognises — images, fonts, media. A `.toml` (or `.csv`, `.zip`,
  …) referenced from a **Markdown link** is silently dropped from `docs/build/1/` and the
  link 404s, with no build warning. Serve the file from `docs/src/public/`, which
  VitePress copies verbatim to the site root. Copy it there in `make.jl`, and *also* into
  `docs/src/assets/` so Documenter's link checker resolves the `assets/…` link:

  ```julia
  # docs/make.jl — before makedocs
  mkpath(joinpath(@__DIR__, "src", "assets"))
  mkpath(joinpath(@__DIR__, "src", "public", "assets"))
  for f in ("Manifest.toml", "Project.toml")
      cp(joinpath(@__DIR__, f), joinpath(@__DIR__, "src", "assets", f); force=true)
      cp(joinpath(@__DIR__, f), joinpath(@__DIR__, "src", "public", "assets", f); force=true)
  end
  ```

  The Markdown link stays relative — `[Manifest.toml](assets/Manifest.toml)`. **Side
  effect**: creating `docs/src/public/` makes DocumenterVitepress **skip its
  `docs/src/assets/ → public/` copy of `logo.*` and `favicon.*`** (guarded by
  `!isdir(src/public)`); stage the logo into `docs/src/public/` in `make.jl` too, or the
  navbar logo disappears. `.gitignore` `docs/src/public/` — it is build output; keep the
  tracked `docs/src/assets/Manifest.toml` as the reviewable snapshot.

- **Local Markdown images render with an empty `alt`.** Every *local* `![alt](file)`
  image — captured plot output and hand-written images alike — is rendered as
  `<img src="…" alt="">`. The alt text is kept only for remote images and for
  `<img alt="…">` inside a `@raw html` block. A CSS hook keyed on `img[alt=""]` (e.g. a
  dark-mode `filter: invert(1)` on white-ground figures) therefore catches **every**
  local image; an image that must be excluded has to be a `@raw html` `<img alt="…">`.

- **`::: details` vs `!!! details`.** For a collapsible block, write the VitePress
  container literally — `@example` blocks inside it still execute. Documenter's
  `!!! details "…"` does **not** produce one: DocumenterVitepress maps every admonition
  category except `tip` / `warning` / `danger` / `caution` to `::: tip`.

  ```markdown
  ::: details Environment used to build this documentation
  …
  :::
  ```

- **No logo / no favicon.** The generated `config.mts` contains two placeholders,
  `logo: 'REPLACE_ME_DOCUMENTER_VITEPRESS'` (in `themeConfig`) and
  `['link', { rel: 'icon', href: 'REPLACE_ME_DOCUMENTER_VITEPRESS_FAVICON' }]` (in
  `head`), filled from `docs/src/assets/logo.{png,svg}` and `docs/src/assets/favicon.ico`.
  When a file is missing, the line is deleted from the built config but a warning is
  emitted on **every** build. A package that ships no logo (the default for
  control-toolbox packages, whose favicon comes from the hosting site) deletes both
  lines from `docs/src/.vitepress/config.mts`: the output is identical and the warnings
  disappear.

- **Theme-adaptive logo.** VitePress's `logo: { light, dark }` **double-renders in the
  DocumenterVitepress navbar title**. Keep the single `logo:` (a light SVG) and recolour
  it in dark mode in `docs/src/.vitepress/theme/style.css`:

  ```css
  /* invert(a) maps white to 255·(1−a); a = 1 − 27/255 ≈ 0.894 lands it on the
     VitePress dark surface #1b1b1f. hue-rotate(180deg) leaves that neutral grey
     untouched and rotates coloured marks back toward their hue (approximately). */
  .dark .VPNavBarTitle .VPImage { filter: invert(0.894) hue-rotate(180deg); }
  ```

  For an in-page hero logo, ship an actual dark SVG (generate it in `make.jl` by swapping
  `#ffffff` → `#1b1b1f`) and swap the two `<img>` with your **own** classes, not
  VitePress's:

  ```html
  <img src="./assets/logo.svg"      class="oc-logo oc-logo--light" />
  <img src="./assets/logo-dark.svg" class="oc-logo oc-logo--dark" />
  <style>
  .oc-logo--dark { display: none; }
  .dark .oc-logo--light { display: none; }
  .dark .oc-logo--dark  { display: block; }
  </style>
  ```

- **Tables are right-aligned by default.** A Markdown table whose separator row has no
  alignment (`| --- |`) is rendered with right-aligned columns. Write the alignment
  explicitly, `| :--- |` for text.

- **Printed output is dropped when a block returns a value.** An `@example` block whose
  last expression is not `nothing` shows that value only; what the block printed (with
  `println`, or a log record) is not shown. End the block with `nothing # hide` to keep
  the printed output, or print the value yourself.

- **Build output** is in `docs/build/1/`, not `docs/build/`; DocumenterVitepress requires
  a git repository.
